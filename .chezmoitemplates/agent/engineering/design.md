# Web・UI/UXデザイン

Web・UI/UXの企画、制作、批評に必要な判断を扱う。既存の要求整理、実装・検証、承認、担当選択・独立レビューの規約を併用する。6項目は反復する検討観点であり、全案件に順番どおりの工程・成果物・承認を追加するものではない。

## 1. 目的と制約を読み取る

- 原依頼、既存画面、利用者・利用場面、ブランド、デザインシステム、対象端末、アクセシビリティ要件を確認する。既知の目的を聞き直さず、設計判断を変える不足や矛盾だけを確認する。
- 確定条件と仮説を分ける。利用者の行動や好みを想像だけで事実にしない。既存の一貫性を尊重し、変更理由のない全面的な作り直しをしない。

## 2. 利用の流れを設計する

- 代表的な利用場面について、開始から目的達成までの操作、必要な情報、判断、画面・状態の変化をつなぐ。画面単体の配置だけで終えない。
- 対象に関係する読み込み中・空・入力誤り・失敗・成功の状態、戻る・取消・再試行の経路を扱う。表示内容と操作結果が利用者に伝わり、入力や作業を失わず復帰できるかを確認する。
- 画面や文言の変更が他の経路へ及ぼす影響を確認する。小さな修正では変更対象と関連する状態に絞る。

## 3. 重要な未決事項を比較する

- 情報構造、主要な操作経路、誤操作からの復帰など、目的達成に影響する未決事項に限り、構造や操作が実質的に異なる案を比較する。判断済みの仕様や小さな変更に案数をノルマ化しない。
- 同じ利用場面・内容・条件で、分かりやすさ、操作の効率、誤りへの強さ、制約への適合を比較する。スケッチや簡易プロトタイプは差を判断できる精度に留める。
- 採用理由、失う利点、未確認の仮説を示す。案の説明を実利用の検証結果として扱わない。

## 4. 見た目の方向性を具体化する

- 対象の内容・利用者・ブランドから、狙う印象と情報の優先順位を定め、文字の大きさ・太さ・行間、配置・整列、余白のリズム、色・コントラスト、画像の役割に落とし込む。「洗練された」等の形容だけで終えない。
- 見出し・本文・主要操作の強弱、情報密度、画像の切り取り、要素間の一貫性を実画面で確認する。既存の部品・トークンを活かし、装飾が内容や操作を圧迫しないよう調整する。
- 外観は使いやすさと並ぶ独立した評価対象とする。操作できるだけで外観を合格にせず、印象・構成・視覚的なまとまりを評価する。個人の好みや流行だけで不合格にしない。
- 見た目の検討で情報構造や操作の問題が見つかれば前の観点へ戻る。確定条件を変える必要があれば依頼元へ戻す。

## 5. 実画面を批評する

- 描画済みの画面またはプロトタイプの対象版、表示幅、状態を特定する。コードだけで見た目を確認済みにせず、静止画だけで操作性を検証済みにしない。確認手段がなければ不足と評価できない範囲を返す。
- **使いやすさ**：情報の発見、操作の理解、結果のフィードバック、失敗からの復帰を利用の流れに沿って確認する。対象に応じてキーボード操作・フォーカス、ラベル、色だけに頼らない伝達、文字拡大や狭い画面での欠落・重なりを確認する。規格適合の表明には指定規格に沿った別の検証が必要。
- **外観**：視覚的階層、文字の読みやすさ、整列・余白・密度、色と画像の関係、狙った印象、画面間・状態間の統一感を確認する。両軸を分けて結果を示す。
- 独立レビューが必要な場合は既存の編成・独立性に従って別視点の担当へ渡す。画面を読める能力・アクセスを確保し、使えない場合は不足を報告する。自己批評を独立レビューと呼ばず、軽微な修正に追加レビュー役を一律に設けない。
- 指摘は「場所・状態／問題／影響／具体的な修正案または方向／確認方法」で示す。観察事実と推測、重要な不具合と任意の改善を区別する。Reviewerは修正の方向を示し、依頼元に代わって解決策を作り込まない。

## 6. 修正し再確認する

- 指摘の採否と理由を整理し、修正後の対象版で影響する画面・状態・操作を再確認する。無関係な箇所まで無制限に磨き続けない。
- 共通の委任・回答形式に、利用場面、比較した重要案と採用理由、画面への参照、使いやすさ・外観それぞれの確認結果と未確認範囲を含める。比較を省略した場合は必要に応じて理由を短く示す。
- AIによる批評と、実際の利用者による評価を区別する。人へ提示する際は成果と確認範囲、残る不確実性を伝え、未実施のユーザーテストや品質改善を実証済みにしない。
