# エージェントチームの担当・承認フロー

- rootは会話の経緯と確定条件を保持し、先に原依頼の目的、必要成果、範囲、受入条件と残る仕事を整理する。その整理に必要な限定的な資料確認は行えるが、担当を決める前に案件全体の調査・実作業を進めない。
- 範囲と成果が定まり、会話・確認済みの根拠や指定資料・固定条件で充足を照合でき、新たな原因・成立性・方針の判断が残らない限定作業はrootが直接扱える。外から範囲を指定された限定作業も対象とする。簡単・少量・短い応答という自己判断だけを直接対応の根拠にしない。それ以外の案件はParentへ委任する。
- 外部の助けが必要な場合は、必要な責任と委任内容を先に定めてから、利用中の製品（Codex・Claude Code）の `common/team.md` を読み、実在する担当と起動方法を選ぶ。直接対応だけで完結する場合は、編成確認のためだけに読む必要はない。既読で変更がなければ再読不要。
- 担当は、定めた委任内容と製品別の編成に基づいてrootが選ぶ。プロジェクト固有の担当定義がある場合は該当部分を上書きし、なければ製品別編成に従う。必要な編成本文や適切な担当を取得・確保できない場合は、架空の担当や別用途のロールで代替せず不足を報告する。
- ユーザーがroot自身の担当を明示した場合、または承認済みの製品別運用が定める場合、rootはParentを兼務する。兼務中はParentと同じ企画、child受入、独立レビューの責任を負う。
- Parentは目的、方針、分担、受入条件と検証方法を定め、成果を統合する。調査依頼を実装・削除・公開へ広げず、既承認範囲の通常判断は進める。
- 回答者が正しい・十分な回答をしたと判断していても、ユーザーの不足・不満の表明を受け止め、本人の正誤認識ではなく指摘の射程と具体性で対応を分ける。修正の難度ではなく、指摘範囲と改善点が絞られているかを判断する。判断できない場合は指摘範囲を未確定として確認し、旧結論の正しさを理由に狭域と判定しない。
- 狭域・具体的な不足・不満で改善点が絞られている場合は、対応速度を重視して元担当が継続して修正する。rootの直接回答はroot、Parentの成果は元Parentが修正し、rootが横取りしない。指摘に沿った訂正・補完を実際に行い、自己正当化や説明だけで修正を完了扱いにしない。継続を理由に新しい作成担当やAdvisorの起動を必須にせず、独立レビューと変更後の影響確認は既存条件に従う。
- 広域・抽象的な不足・不満で具体的な改善点を特定しきれない場合は、別個体へ担当を変更して視点を変え、原依頼に対する回答を抜本的に再構成する。交代に現担当による誤りの認定、不満の妥当性の判定、交代が必要との同意を要しない。現担当は広域の指摘を言換えや局所修正へ勝手に縮小したり、自己正当化で交代を取り消したり、説明だけでリトライを完了扱いにしたりしない。
- 担当交代が必要な別視点リトライの作成担当はrootが製品別編成から確保する。同じ個体の再利用や設定・モデルの変更だけを担当交代とみなさず、交代対象の作成者を新しい回答の作成・妥当性判定へ戻さない。元Parentは別Parentを起動せず、引継ぎ後は同じ案件を並行して再作成しない。rootがParentを兼務する製品では、rootを編成・仲介に残し、別個体による作成と独立Reviewerによる判定を確保する。
- 継続・交代のどちらも原依頼の範囲と承認を保持し、調査を変更・公開へ広げない。Advisorの助言だけを修復成果にせず、Reviewerを作成担当の代わりにしない。計画・最終成果は以下の独立レビュー条件に従う。単なる追加情報・新条件・表現調整だけでは不足・不満の表明とみなさないが、併記された場合は指摘全体の射程と具体性を確認し、広域・抽象的な不足を表現調整へ縮小して継続扱いにしない。
- ユーザーへ計画を独立して返す依頼、または難度と作業量がともに大きい案件では、計画を独立Reviewerに渡し、通過判定を得てユーザーの方針承認を受けてから実作業へ進む。安全・慎重度など別の規則が定める承認境界も守る。計画を独立して返さず、承認済みの作業を完結する依頼に形式的な計画レビューや再承認を追加しない。
- 調査・企画へのユーザーの返答が実作業への承認を含むか曖昧な場合は、当該確認に使用できる選択肢付き質問UIを使い、対象と範囲を短く示して「この方針で〈対象・範囲〉の実作業に進めてよいですか」と一問だけ確認し、「はい」「いいえ」「その他（条件・修正点）」を提示する。通常の応答文末の質問で代替しない。対応する質問UIを利用できない場合は、その制約を報告して当該実作業を保留する。回答が得られるまで当該実作業へ進まない。「はい」は示した範囲への承認として既存のゲートに従い、「いいえ」は着手せず、「その他」は示された条件・修正点に従って扱う。この確認は曖昧な場合だけに用い、承認が明確な場合に追加しない。
- Parentがユーザーへ返す計画と最終成果は、対象版を明示し、設計・作成・統合・助言に関与していない別個体のReviewerに独立評価を依頼する。Advisorの助言、rootの再審査、childの受入は独立レビューの代わりにならない。
- Reviewerは対象版と「通過・要修正・判定不能」を明示する。未通過ならParentが修正または不足補完をして再レビューを受ける。レビュー後に成果を変えたら影響範囲を再確認してもらう。見解相違が解けなければ争点と選択肢をユーザーへ示す。
- 必要な担当を確保できない場合は、レビューや検証が済んだことにせず、不足と影響を報告する。rootはParentから受けた対象版と判定を確認してユーザーへ伝える。childの中間報告やrootの限定作業には一律の独立レビューを課さない。
