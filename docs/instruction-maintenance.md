# 指示文書の保守ルール

## 対象と位置づけ

本書は、このリポジトリの指示・テンプレート・説明資料を編集するメンテナ向けの正本である。通常業務を行うエージェントへの行動指示ではなく、配布・includeの対象にしない。配布先の変更やchezmoi実行の許可も与えない。

本書は文書の責務と配置を定める。業務上の権限・承認・行動原則は対応する運用文書が定める。既存文書がこの構造に適合済みであることを意味せず、整理時も合意済みの意味・例外・承認条件を保持する。

## 担当ごとの受領時点

全担当は `rules/core.md` を直接受領する。委任の共通契約 `team/interface.md` は全専用設定と両製品の `common/interface.md.tmpl` から直接includeする。専用Parent・末端担当は起動時、root・兼務Parentは初回委任前に受領し、既読不変なら再読しない。root/planning入口へ共通契約を重複includeしない。Parentと末端担当への必要安全の配布は、グローバル指示を継承するかどうかに依存しない。汎用入口に実作業の詳細を常設しない。

| 担当 | 起動時の専用本文 | 追加で読む時点 |
| --- | --- | --- |
| root | グローバル入口のcoreと短い導線 | 案件開始時にcommon/root.md。責任・委任内容確定後、外部起動が必要ならcommon/team.md |
| Parent | coreとteam/planning.md | child起動前にcommon/team.md。自らコード調査・実装・検証する前はcommon/implementation.mdと必要資料 |
| Worker | core、team/child.md、team/worker.md | 実作業前にcommon/implementation.md、対象の開発・言語・TDD/lint/Git等 |
| Reviewer・Advisor・assistant | core、team/child.md、担当別本文 | 委任された案件資料・必要な個別規約。実装詳細は一括配布しない |

Parent兼務rootは企画前にcommon/planning.md、rootの限定実作業でもcommon/implementation.mdを読む。ClaudeではrootがParentを兼務する。操作・記録の前はcommon/operations.mdを確認する。既読不変なら再読不要。必読資料が取得できなければ該当行為を進めない。

## 用語の表記

Codexの会話全体を担当するエージェントは、小文字の `root` に統一する。階層名と仕事の役割の区別は [チームの全体像](codex-subagents.md) に示す。設定の識別子・ファイル名、過去の原文引用は表記統一のために改変しない。

## 配置を決める順序

1. 追加する内容が「業務の行動規則」「ロール固有の手順・設定」「人向けの説明」「メンテナの編集規則」のどれかを決める。
2. 対象読者と、その情報が必要になる場面を特定する。全員に必要なら共通本文、特定ロールだけならその本文へ置く。
3. 同じ判断を既に定める正本を検索する。存在するならそこを修正し、別の場所に補足規則を積み上げない。
4. 新規文書に分けるのは、読者・読む契機・更新理由が独立し、参照経路を維持できる場合とする。文字数だけで細分化しない。

## 重複と参照の基準

- 一つの判断規則には一つの正本を置く。正本以外には、必要な短い要約と参照先だけを置き、条件・例外を独自に追加しない。
- includeによる同じ本文の配布は、手書きの重複とは区別する。各担当に必要な本文が届くことを優先するが、取り込み後に同じ説明を再記述しない。
- 必須のcoreはグローバル入口と全専用設定から直接includeする。Parentはplanning、末端はchildと担当別本文も直接includeする。条件読込のroot/implementation/operations等は両製品のcommonテンプレートから直接includeして配布する。共有Markdownに評価されない入れ子のincludeを置かない。
- 参照だけで届くと仮定しない。通常業務の担当が保守用docsを読まなくても動けるよう、必要な指示は配布される本文に含めるか、実際に読める配布先と読む契機を指定する。
- sourceの相対リンクと配布先の参照を区別する。メンテナ向け資料ではsourceへリンクし、運用本文に配布されないdocsへの必須参照を作らない。
- ロール側には「この担当が何を受け取り、何を判断し、何を返すか」を書く。依頼側には「いつ誰へ何を渡し、結果をどう扱うか」を書く。同じ受け渡しを両側から説明しても、共通原則や相手の手順全文は繰り返さない。
- 人向けの図・比較表は正本の説明として再掲できる。正本へのリンクを付け、正本変更時に追従させる。受入ケースは規則の具体化であり、新たな権限や例外を追加する場所にしない。
- 入口文書には詳細へ進むための要点を残す。重要な制約を削って短くするのではなく、判断の分岐が増える箇所を適切な正本へ移す。

## 変更と確認の手順

1. 変更前に、変更する判断規則、その正本、include・参照元、影響するロールと説明資料を特定する。
2. 内容を変える変更と、意味を保つ移動・重複除去を区別し、承認範囲を確認する。整理を理由に未承認の権限変更を混ぜない。
3. 正本を更新し、依存する本文・説明・リンクを同じ変更で合わせる。切り出した本文への入口を確保してから旧記述を整理する。過去の説明を残す場合は履歴であると明示する。
4. sourceの検索・差分確認で、同じ規則の別表現、古い例外、参照切れ、共通本文の再説明が残っていないか確認する。文書単体だけでなく、対象ロールが受け取る本文全体で確認する。
5. 既存の構文・include検証に加え、通常経路・例外・未解決時の受け渡しを具体例で照合する。静的な照合と実際のモデル動作試験を区別する。chezmoi実行と実環境反映には別途明示指示が必要である。

完了時は、正本の配置、削減した重複、保持した条件・例外、検証と未検証範囲を報告する。構文検査が通っただけで読みやすさや行動の改善を実証済みとしない。

## 運用上の確認

### 指示の読込量を計測する

指示本文・include・参照条件を変更するときは、次のコマンドで変更前後を比較する。Python 3.9以降の標準ライブラリだけを使い、chezmoiやテンプレート内の処理を実行しない。

```sh
python3 scripts/measure-instructions.py
python3 scripts/measure-instructions.py --format json
python3 -B -m unittest discover -s scripts -p 'test_*.py'
```

- 主指標は担当×業務の総読込文字数。初期読込は全専用ロールを別ケースにする。各ケースは独立して計測し、異なる担当へ同じ安全規約を配ることを重複削減の対象にしない。
- Unicodeコードポイント数で数え、空白・改行を含む。改行はLFへ正規化し、トークン数・課金額・実測コンテキスト量とは呼ばない。案件資料・依頼文・ツール出力は対象外。グローバル指示や履歴の継承はケースで明記し、専用設定へ暗黙加算しない。
- `include "相対パス"` を再帰展開する。Codexは改行直後から始まる三重引用符の `developer_instructions` 本文のみ、Claudeは先頭frontmatterを除く本文を数える。Codex本文のエスケープや他のテンプレート式等、未対応の構文はエラーにし、推定で通さない。
- 総読込文字数は同じ本文の再登場も数える。固有本文文字数は同一sourceファイルの同じ区間を一度だけ数える。重複文字数はその差。同文でも異なるsourceに手書きされたものは自動重複判定しない。意味上の重複は別途レビューする。
- ファイル読込回数は入口とinclude先の出現回数、固有ファイル数はその異なり数。実ツール呼出回数ではない。出力にはケース条件、読込理由、展開先一覧・出現回数を含める。
- 自然言語の参照条件は自動解析しない。ケース定義に読込順と理由を明記する。既読不変で再読不要な参照は一度だけ列挙するが、複数入口に埋め込まれた同じ本文は重複として数える。
- 新規ガイド・読込条件・ロールの追加や廃止時はケース定義も確認する。対象業務の意味を維持した経路変更と、業務・検証範囲を狭める変更を区別し、削減を過大評価しない。ケースの追加・削除・定義変更はレポートで明示される。
- CIは計測エラー（欠落・循環・未対応構文等）を失敗にする。文字数増加には理由を付けてレビューし、増加だけでは失敗にしない。必要な安全・承認条件の欠落で数値を改善しない。一律上限・削減率は現時点で設けない。
- 基準値は2026-11-06の整理前sourceを初期値とする。基準更新は計測方法・ケース条件・増減理由をレビューしてから、次の明示コマンドで行う。通常実行・CIでは更新しない。計測方法変更時はmeasurement_versionも変更し、旧値との単純比較を避ける。

```sh
python3 scripts/measure-instructions.py --write-baseline
```

基準値には本文そのものや端末固有絶対パスを保存しない。基準値更新の理由と前後差を変更説明に残す。計測器・テストは `scripts/`、ケースと基準値は `docs/` に置き、いずれも配布対象外とする。

本書の追加だけで既存文書の整理完了とはしない。整理ごとに対象・保持条件・検証結果を確認する。共通の安全・承認境界はcore、担当選択・移管・承認仲介はroot、企画・受入・独立レビューはplanning、末端責務はchildと担当別本文、実作業はengineeringが所有する。全ロールは共通原則を明示的に取り込む。保守用docsを運用時の必須参照にしない。

## モデル・effortの決定根拠を残す

- 設定の正本は各TOML。現段階の解釈・根拠・変遷は [モデル選択資料](codex-agent-model-selection.md) に集約し、運用本文へ調査経緯を持ち込まない。
- 定義上選べるeffortと、担当業務で実用上選ぶ価値のあるeffortを区別する。高effortによる能力向上を線形と仮定しない。
- 見直しごとに日付、旧設定、新設定、対象の呼出元・仕事、採用理由、反証・限界、未確認事項を残す。過去の結論を根拠ごと消さず、変更履歴として要約する。
- 根拠を公式仕様・公開ベンチマーク・フォーラムの経験談・利用者の観測・運用上の判断に分ける。出典URL、確認日、比較条件を残し、確認できなかったことを測定事実にしない。
- 価格はAPI単価、Codexの利用枠、実測の総費用を区別する。初回の速度・単価だけでなく、指示・受入・再作業の負担も考慮する。未取得の数値を推定で埋めない。
- 公開ベンチマークによる弱い支持、実運用での満足、最適性の実証を区別する。総合点から個別ロールの品質を直接保証せず、設定維持を消極的に選ぶ場合も代案を採らない理由を残す。
- 案件ごとの条件差と測定負担を踏まえ、再現性のある統計比較を運用上の設定判断の前提にしない。満足度、指摘の納得感、意図の理解、手戻り感、待ち時間・費用の負担感などの弱い指標を使う。採点や全件記録を義務化せず、具体例と判断理由を必要な範囲で残す。
- 使用感の変化をモデル単独の性能差と断定しない。指示や分担の影響も考慮し、問題の顕在化や有用な公開情報を契機に見直す。比較試験の未実施だけを理由に設定を保留・変更し続けない。
- 設定を変える際は呼出元とReviewerとの関係、プロンプトの適合、受入ケース、説明資料とCIを同時に確認する。未検証の候補は暫定と明示する。
